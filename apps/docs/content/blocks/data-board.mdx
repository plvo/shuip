`DataBoard` renders any array of typed items into draggable columns and stays usable when that
array grows: the board has a finite height with sticky column headers, each column scrolls on its
own, and cards are paginated per column. Columns, card fields, grouping and search are all
configured against your own data shape — nothing is hardcoded to a domain.

### Built-in features

- **Generic data model**: works with any item type `T` via `idField` / `columnField`.
- **Bounded height**: sticky column headers, one scroll container per column.
- **Grouping into bands**: `groupBy` any field to get collapsible horizontal bands; dropping a card
  in another band emits the new value.
- **Per-column pagination**: a "show more" step per column, or one per band when grouped.
- **Hideable columns**: hide from the header, recall from the right-hand rail.
- **Persisted view**: hidden columns, page size and collapsed bands survive a reload via `persistKey`.
- **Global search**: filter cards across `searchableFields`.
- **Ordered cards**: name a numeric field in `positionField` and each column keeps its cards sorted by it.
- **Hybrid state**: standalone from `defaultData`, or controlled via `data` + `onDataChange`.

> Cards become draggable as soon as you pass either `onCardMove` or `onDataChange`. A board that passes neither is genuinely read-only — the cards have no drag handle at all.

> Without `positionField`, card order is implicit in the `data` array order. On any move the board
> emits the reordered array via `onDataChange` and a semantic `onCardMove` event; map either to your
> own persistence. To store the order of cards as a number instead, see [Keeping the order of cards](#keeping-the-order-of-cards).

## Choosing between Kanban and Data Board

Both are drag-and-drop boards. Pick on volume and on how much view control your users need.

| | [`kanban`](/blocks/kanban) | `data-board` |
| --- | --- | --- |
| Height | grows with the tallest column | bounded, sticky headers, per-column scroll |
| Volume | tens of cards | hundreds, via pagination |
| Grouping | none | `groupBy` any field, collapsible bands |
| Columns | fixed | hideable, with a recall rail |
| View persistence | none | `localStorage` via `persistKey` |
| Size | small | larger surface, more props |

If a board fits on one screen and users never need to hide a column, `kanban` is the smaller and
simpler install.

## Sizing the board

The board is `flex min-h-0 flex-col` and fills the height its parent gives it — so it never needs
to know the page chrome around it, and there is no hardcoded `calc()`. The contract is on the
parent:

```tsx
<div className='flex h-[calc(100svh-4rem)] flex-col'>
  <DataBoard {...props} />
</div>
```

Where the parent constrains nothing, pass `height` instead. A number is read as pixels.

```tsx
<DataBoard height={520} {...props} />
```

## Column accents

The block ships no palette — it would impose a theme on your app. A column takes a Lucide `icon`
and an `accentClassName` applied to it, so the semantics stay yours:

```tsx
const columns: DataBoardColumn[] = [
  { id: 'todo', label: 'To do', icon: CircleDashed },
  { id: 'doing', label: 'Doing', icon: CircleDot, accentClassName: 'text-primary' },
  { id: 'blocked', label: 'Blocked', icon: CircleX, accentClassName: 'text-destructive' },
  { id: 'done', label: 'Done', icon: CircleCheck, accentClassName: 'text-emerald-600' },
];
```

## Keeping the order of cards

Name a numeric field of your items in `positionField` and the board sorts every cell by it, in
ascending order. A cell is a column, or one column of a band on a grouped board, so positions never
interact between bands. Cards of equal position keep their order from `data`, and a value that is not
a finite number (missing, `null`, `NaN`) counts as `0`.

```tsx
<DataBoard<Task> positionField='position' {...props} />
```

On drop, the board writes a new position into the moved card. It is computed from the neighbours of
the landing slot in the **full** order of the target cell: cards hidden by pagination or by search
count as neighbours, so a drop never jumps over a card the user cannot see, and the dragged card does
not count.

| Landing slot | New position |
| --- | --- |
| Empty cell | `0` |
| First | next position `- 1` |
| Last | previous position `+ 1` |
| Between two cards | midpoint of their positions |

The moved card comes back from `onDataChange` with the field overwritten, and `onCardMove` carries the
same value as `position`, so persisting a move is one update of one record:

```tsx
<DataBoard<Task>
  columnField='status'
  positionField='position'
  onCardMove={({ item, toColumn, position }) => updateTask(item.id, { status: toColumn, position })}
  {...props}
/>
```

The next list is complete, with the moved card in its place: feed it back through `data` and the
board shows exactly what you stored. The list comes sorted by position, with equal positions in their
previous order.

The neighbours of the moved card are named on every move event, with or without `positionField`.
`beforeId` and `afterId` are the ids of the cards right before and right after it in the full order of
its new cell, and `null` at the edges. Use them to store the order as a linked list, or to call an API
that takes an `afterId`.

Each move halves the gap between two neighbours. A consumer that moves cards into the same gap
thousands of times eventually runs out of float precision, and the board does not renumber
positions for you: renumber the cell on your side when the gaps get too small.

## Notes and limitations

- **`toIndex` is a whole-column index, including in grouped mode.** When `groupBy` is active, the
  `toIndex` on `onCardMove` reflects the card's position within its entire column, not its position
  inside the band the user sees. If you persist a rank, compute it from the item's position within
  its group rather than from `toIndex` directly.
- **Dropping into a declared-but-empty group writes the group's id as a string.** When
  `groupBy.groups` declares a group that currently holds no items, the board has no item from which
  to learn the field's real type, so a card dropped there receives the group's `id` as a string. If
  the grouped field is numeric, coerce the value in `onCardMove` until the group holds at least one
  item.
- **Cards move on drop, not on hover.** While a card is held, the others stay where they are and a
  drop slot of the card's height shows where it would land. The move is applied once, when the card
  is released: right after the card it was held below, right before the card it was held above, or at
  right after the last card shown when it is released on the column itself, so it never jumps over
  a card hidden by pagination or search. Releasing a card outside any
  column, on its own slot, or pressing Escape leaves the board as it was and fires neither
  `onCardMove` nor `onDataChange`.
